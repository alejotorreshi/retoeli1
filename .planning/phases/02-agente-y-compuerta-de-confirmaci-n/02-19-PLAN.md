User decision (locked in this planning session, 2026-10-13, Option A, chosen because PRD CA3 and RN4 require it). Record it as D-63.6, which supersedes the D-37 sentence "Cualquier otro mensaje cancela lo pendiente":
- With a case pending, a reply classified otro KEEPS the case pending. The server re-appends its own deterministic closing question (case and bloqueos) to that turn's reply, with needsConfirmation true and confirmation_required emitted, so the front highlights it (CA3). The analyst's next "sí" or "envía" authorizes the send on the immediately following turn (RN4).
- Only an explicit rejection (the classifier's rechaza, or the button with aprobada false) cancels the pending case.
- An unrelated instruction such as "procesa el caso Y" is processed normally. The earlier case stays pending and its question is re-appended; it never blocks or hijacks the new work.
- Planner reading of the same rule, recorded in D-63.6: confirming one of several pending cases authorizes that case only and keeps the others pending; a confirmation that names a case that is not pending authorizes nothing and keeps the pending cases; an aborted turn still closes LIBRE, because the analyst saw no question.
- Revision 1 (plan check, same Option A): a confirmation turn that ends final without using its grant (the model answered with text only) re-opens the case like error and tope already do (D-63.2), so the server re-appends its question. Today recuperarAutorizado returns [] for that ending (compuerta.policy.ts:131), which drops the case although the analyst never rejected it. Only the pending state comes back; the grant stays consumed (D-38) and the next send needs a fresh explicit confirmation. D-63.6 then lists every way a pending case leaves the gate without a send: an explicit rejection, a caller abort and the end of the session (D-58).
- The model never writes the confirmation question or a confirmation request (02-18 prohibition). prompt.md and the knowledge are aligned, and the misleading CR-01 loop test is fixed.

Purpose: restore ENV-03 (the turn that waits for a confirmation always ends with the server question, its bloqueos and needsConfirmation) and the RN4 path of ENV-02, and give DEMO-03 the loop test of the script the prompt prescribes, the one that would have caught CR-01.
